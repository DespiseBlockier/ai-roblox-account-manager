A native Windows account manager with the familiar account-list and join-server workflow of [ic3w0lf22's Roblox Account Manager](https://github.com/ic3w0lf22/Roblox-Account-Manager). This is a fresh implementation, not a repackaged upstream executable. No original release binaries or bundled assets are used.

## Start

Close any older manager window, then double-click **Start.cmd**, or open **dist/v1.10.0/RobloxAccountManager.exe**. For the shareable build, extract `releases/RobloxAccountManager-1.10.0-win-x64.zip` and open `RobloxAccountManager.exe` inside its `RobloxAccountManager` folder. Keep the entire folder together.

On first launch, create a **master password**. Any nonempty password up to 1,024 characters is accepted; 12+ characters are recommended. Shorter passwords show a nonblocking **Not secure** reminder. With password protection, your accounts, saved passwords, cookies, groups, and game data are encrypted in `Data/accounts.vault` beside the executable. Protected vaults require that password each launch. Keep it safe; the app cannot recover it.

You can instead select **No master password (Not recommended)** and acknowledge its warning. This stores saved passwords, cookies, and account data in readable form and opens the app without asking for a password. Anyone who obtains the folder can access those accounts. This option is off by default. **Vault security…** changes the setting later; removing protection requires the current master password. Enabling protection encrypts both the current vault and its known previous-save file. This cannot securely erase plaintext that already existed on the drive or in other copies.

**Authenticator-app 2FA:** open **Vault security… → Set up authenticator…** after enabling a master password. Scan the displayed QR code with your authenticator app, or enter its setup key manually using time-based (TOTP), SHA1, six-digit, 30-second codes, then confirm a code. The QR code is generated entirely offline in memory; the setup secret is never sent to a QR service or saved as an image. Save the eight one-use recovery codes somewhere separate from the vault. Normal launches require the master password plus an authenticator or unused recovery code, including launches with a command-line password. Codes from an accepted time step cannot be reused; wait for a fresh code when changing security settings. Vault security also lets you generate replacement recovery codes or disable 2FA, requiring the current master password and a valid code. New recovery codes invalidate every previous recovery code. Losing both the authenticator and recovery codes means this app cannot unlock the vault.

This is a **local app-unlock check**, not an independent layer of offline encryption. The authenticator secret is stored inside the master-password-encrypted vault. Someone who has the vault file and knows the master password can bypass this check using other software. It does not configure Roblox account 2FA. Authenticator-enabled vaults use a newer authenticated header that older manager versions cannot open. The setup key, recovery hashes, and consumed-code state stay in the private vault and are excluded from layout exports. Updates use the existing one-use session handoff only after both unlock steps have succeeded; later normal launches ask again.

To use a USB or another PC, close the manager, copy the **whole used application folder including Data**, and open it on the other PC. Protected vaults use the same master password; no-password vaults open automatically. Browser caches stay under Data in separate per-PC/per-Windows-user directories. The portable vault restores saved cookies into the matching account's new browser profile; Roblox may still require a fresh login or verification on another PC. All account entries and saved passwords remain in the vault.

The first-run screen can import your older Windows-bound manager vault from this PC. This happens only when you create/unlock the app, never while building the release. The original old installation is preserved. If directly opening an old vault through `--data-dir`, convert it on the original PC using the conversion screen. Layout backups still exclude credentials; copying your private Data folder carries the complete vault.

The release targets **Windows x64** and includes the .NET runtime. [Microsoft Edge WebView2 Runtime](https://developer.microsoft.com/en-us/microsoft-edge/webview2/) must be installed on the PC. The manager runs as a normal user and needs a writable application folder.

1. Click **Add account ▾** and choose **Browser login** or **Bulk sign in**. The separate single username/password form has been removed.
2. **Bulk sign in** has three formats. `username:password;group;"Note"` accepts an optional local manager group and note. Quote fields containing semicolons and double quotes inside quoted fields: `account_one:"pass;word";Alts;"Note; with ""quotes"""`. Missing group/note fields keep existing values; an explicit empty note clears it after verified login. `username:password` treats everything after the first colon as the password, preserving spaces, colons, and semicolons. **Cookie login** accepts one raw `.ROBLOSECURITY` value per line, optionally prefixed with `.ROBLOSECURITY=`. Cookies are verified through Roblox before saving; existing accounts are matched by verified user ID, and their saved passwords are kept. Invalid cookies are skipped; rate limiting stops the batch. The limit is 500 entries, with 4,000 characters per note. The group is a local manager group, not a Roblox community.
3. Each credential-based bulk sign-in browser opens restored and focused in the foreground. Each queued account opens the actual `https://www.roblox.com/login` page. For credential sign-in (a bulk entry or a saved-password reconnect), supplied details are filled and **Log In** is pressed automatically once the button is ready. Complete Roblox verification yourself. **Browser login** stays manual; a reconnect without a saved password also stays manual. Automatic submission does not retry after a login error or page reload, and never marks an account connected until its identity is verified. A verified session is detected automatically and the next queued account opens. **Connect account** remains available as a manual retry. Bulk login browsers also have **Skip account →**: it closes and discards that pending login, then advances. Skips are counted separately from connected accounts; skipping the last entry finishes the queue. Closing the browser normally still stops the entire queue.
4. A new account row and its credentials are saved only after Roblox confirms the intended username. Closing the sign-in browser stops the queue and discards remaining unsaved logins. Successfully connected accounts stay saved. Repeated Add clicks resume the current login instead of adding placeholders. Old default placeholders from v1.0 are removed on startup.
5. Select an account, enter a place ID or game link, and click **Join server**. Roblox must already be installed. A launch request is not proof that the player successfully joined. Each account has its own browser profile, separate from your regular browser.

The bulk entry box displays pasted passwords or cookies while you edit it and clears when the queue starts or the dialog closes. It has no undo history. No import list is written to disk. Cookie imports mark their browser profile for refresh so a stale profile does not override the new verified cookie.

**Session validity:** saved cookies are checked on startup, every five minutes, and with **Check status**. Rows distinguish valid sessions, expired cookies, verification requirements, and transient check failures. Hover the session text for its last-check time. Network errors and rate limits do not prove that a cookie has expired. Checks pause while adding accounts and stop a batch if Roblox rate limits it.

**Age group:** the Status column replaces the old “Never launched” label with the age bracket reported by Roblox (for example, 13–15, 16–17, 18–20, or 21+). Startup checks, the five-minute status check, and **Check status** refresh it after confirming the account identity. Roblox's age-check flag takes priority: accounts that have not completed an age check show **Unchecked**, even if the birthday-based bracket says 21+. A bracket is shown only when Roblox explicitly reports a completed age check. Hover for the age-check state, last successful refresh, and any failure. Missing status or unsupported brackets show **Unknown**; failed requests keep the last confirmed status. Brackets cached by older versions remain hidden until the age-check state is confirmed. Only the bracket and check time are saved in the private vault. Birth dates and verification documents are not requested or saved. Layout exports exclude this cached information.

**Ban monitoring:** the same checks read Roblox's moderation status. Restricted accounts are highlighted red, including when selected. The row shows the ban duration and end time when Roblox supplies dates. **Ban status** shows full dates, Roblox's message, and the last successful check. When the end time passes, the label changes to **Expired · reactivate**; open the account browser to review/reactivate. This does not automatically accept a moderation notice or confirm that Roblox has removed the restriction. Warnings appear separately, and missing dates show an unknown duration rather than guessing a permanent ban. Failed requests retain the last known result and show the failed check in the details. Cached results travel with the private vault; they are not included in layout exports.

**Reconnect:** select an expired account and click **Sign in · use saved login**. The browser fills its username and saved password, presses Log In once if a saved password exists, and the refreshed cookie is stored after a verified login. **Password…** lets you edit or forget a locally saved password without changing it on Roblox. Browser-only login cannot save a password that was never provided to the manager; use Password… to add one afterward. Browsers never capture manually typed password fields.

**Notes:** each account has an inline note preview in the list. Select an account and open the **Notes** tab beside Launch to read and edit its full note without opening Edit. **Save notes** stores pending notes in one write. Unsaved drafts stay available when switching accounts and save when closing the manager or starting another account operation. A failed save keeps the drafts and blocks closing so they are not silently lost. Notes use the vault's current protection setting.

**Bulk edit:** select accounts with Ctrl/Shift and click **Bulk edit…** (or Edit with multiple accounts selected). Check the fields to change: group, alias, notes, and favorite. Preview the results before applying. Alias templates accept `{username}`, `{displayName}`, and `{index}`. Notes can be replaced or appended. Unchecked fields and credentials stay unchanged; a failed save rolls the whole edit back. Use the existing Save target action to set a game target for multiple selected accounts.

**Browser code:** click **Open browser with code…** to open the code editor. The adjacent **JS docs** and **Examples** buttons open separate windows. JS docs contains the offline ram reference. Examples contains ready-to-edit scripts for account/guest starters, saving the current account, creating one account and saving it, CAPTCHA detection/solver requests, and joining a group. **Use example** copies the selected script into the editor; it never starts execution. The separate example generator has been removed. For the join-group example, edit `groupId` in the code and enter the matching ID in native membership confirmation. Native verification waits for actual membership; pending approval is not membership. `ram.done()` closes the browser and advances; `ram.stop()` stops the queue. Run only code you trust.

**Guest browsers:** clear selection with **Clear selection** or by clicking empty space outside the account rows and interactive controls. **Open browser** then opens a fresh private guest session. **Open browser with code…** also works with no selection; it runs once in a fresh private session with `ram.account === null`. Guest sessions do not restore saved cookies or automatically add an account, even if you sign in manually. An explicit `ram.addAccount()` call can save their current authenticated account. Saved-account code runs still verify identity before execution and completion; guest runs cannot use native group-membership confirmation.

**Save from browser code:** `const saved = await ram.addAccount(optionalPassword)` verifies the current browser session with Roblox and saves its account and cookie using the active vault protection. The optional password is explicitly supplied by your script; omitting it preserves an existing saved password or leaves a new entry without one. It does not validate or change that password on Roblox. Existing entries are matched by verified user ID without overwriting their group/notes. The result contains only `success`, `userId`, and `username`; it never exposes the cookie or saved passwords to JavaScript. Failed identity checks, signed-out sessions, and failed writes do not add placeholders. A selected-account browser must still match its selected user. Saving completes before the promise resolves; stopping afterward does not undo it. See Examples → Save current account.

**Create and save one account:** clear account selection, open the code editor, then **Examples → Create account and save → Use example**. Fill in your own username/password, real birthday, Solvex API key, and proxy; read Roblox's terms/privacy policy before enabling `acceptTerms`. `await ram.createAccount(options)` uses a fresh native session through that proxy, detects a signup CAPTCHA if requested, obtains one Solvex solution, submits Roblox's challenge continuation, and retries signup with the proof. It uses the returned solver user agent and the same proxy for Roblox requests. Only a successful signup followed by a matching authenticated identity can save the new password and cookie into the active vault. The result exposes identity and save status only; no session cookie. Guest mode only, one signup per run, no automatic username/paid-task retry loops. Unsupported verification, rejection, and rate limiting stop the attempt. If a request times out or you stop, check the username before retrying. An account created successfully but not saved must be added through browser sign-in. Solvex may charge for the submitted CAPTCHA. The example and full protocol are tested with simulated responses; no live signup has been verified, and external changes may require an update.

**Solver JS helpers:** the offline **Docs** tab includes `ram.capsolver.register(key)`, `ram.solvex.register(key, proxyOptions)`, `await solver.status()`, `ram.fetchcaptcha()` (also `ram.featchcaptcha()`), and `await solver.solvecaptcha(captcha)`. Status resolves to a boolean; solve resolves to `{success, token, solution, errorCode, message}`. Readable widget/iframe configuration is detected for reCAPTCHA v2, Turnstile, and FunCaptcha; unavailable configuration returns null. Explicit provider task objects are also accepted. Solutions are returned to your script and are not automatically inserted into Roblox. A provider token does not prove the site accepted it.

Solvex requires proxy settings and a current challenge blob. CapSolver's current task catalogue does not list FunCaptcha, so those tasks return an unsupported-type result before creating a paid task. Session-bound challenges may still need manual verification. See the [Solvex API reference](https://solvex.run/docs) and [CapSolver task catalogue](https://docs.capsolver.com/en/guide/api-tasktype/). Keys are supplied explicitly in your script, kept out of the vault, and cleared from the editor on close. Scripts and the page they run on can see supplied script secrets; use only code and pages you trust. The app never automatically forwards saved Roblox passwords or the browser cookie jar to a solver. Only the fixed official HTTPS API hosts are used, with redirects, callbacks, and arbitrary host overrides blocked. Solves may incur provider charges; each call creates at most one task, with bounded polling and cancellation. Stopping cannot undo a request already submitted.

## Features

- Dark custom title bars with normal move, resize, minimize, maximize, and close controls; matching scrollbars, dropdowns, menus, and dialogs. Windows-owned file pickers follow the Windows theme.
- Multiple account entries, aliases, notes, editable groups, search, starred accounts, and manual ordering.
- Separate persistent browser sessions, verified against the selected Roblox user ID before every managed launch.
- Place IDs, game URLs, optional public-server Job IDs, and per-account saved game targets.
- Public server browser with pagination, player counts, server-reported ping/FPS, and smallest-first sorting.
- Game favorites and the last 30 requested game targets.
- Multi-selection for session checks, launch requests, group-independent edits to favorites, saved targets, local sign out, and removal. Select rows using Ctrl/Shift.
- Optional portable AES-256-GCM master-password encryption for account details, explicitly provided passwords, and Roblox session cookies. Short passwords show a warning instead of being blocked. No-password mode is clearly marked Not recommended. A flushed temporary file replaces the vault while retaining the previous save under its active protection mode.
- Optional authenticator-app unlock checks and one-use recovery codes in Vault security (requires a master password; see limitations above).
- Password-encrypted layout export/import using PBKDF2-SHA256 and AES-256-GCM. Imported accounts get fresh profile IDs and must sign in again. These backups **do not contain login sessions**.
- Optional, off-by-default legacy multi-instance mutex. Enable with Roblox closed. Modern Roblox clients may ignore this method or limit simultaneous clients. It does not modify Roblox files, inject code, close other processes, or bypass client protections.

Private server links (including `/share?code=...&type=Server`) open in the selected account's browser. Click **Play** on Roblox there. Private-server access permissions still apply. Multiple accounts launch sequentially; Roblox may replace an existing client when multi-instance is unavailable.

## What differs from the reference

The interface follows the same workflow with a new dark layout. This is not an exact feature-for-feature clone. It replaces the updater with a publisher-verified updater with manual installation by default and optional automatic updates and omits the network control API, WebSocket account control, password-field capture, cookie/ticket clipboard export, plugin loading, client patching, and automated changes to account credentials. Login autofill only uses explicitly supplied credentials on Roblox's official login page and makes at most one automatic Log In click per explicit credential-based attempt. It waits for an enabled button, leaves regular browser login manual, and does not solve verification challenges. Solver requests happen only when your explicitly started script calls a solver helper. Browser code runs only when explicitly started in its editor; it is never downloaded or run automatically. The reference source review focused on account/session, storage, browser, updater, and network-control workflows; it was not a forensic audit of all original release binaries.

## Local data

All new manager data is under **Data beside the executable**:

- `accounts.vault`: account details, saved passwords, session cookies, cached moderation and age-group results, groups, favorites, recent targets, saved links, and optional authenticator settings, and app preferences. Encrypted with a master password by default; readable when No master password is enabled.
- `accounts.vault.previous`: the previous save, using the protection mode that was active when it was saved. Removed account details or credentials can remain in this previous copy until another successful save.
- `BrowserData/<device key>`: WebView2's browser storage for each PC/Windows user, including browser-protected cookies. Treat the entire Data folder as private.

**Sign out** clears the selected browser profile and its saved cookie; the saved password is kept for reconnecting. **Remove** clears that profile and removes its entry and credentials from the current vault. Neither revokes sessions on other devices or stops a Roblox player already running. To revoke sessions, use Roblox's own security settings. A canceled new login's temporary profile is cleared; old v1.0 orphan profiles are not automatically deleted during placeholder migration.

The app does not read your regular browser, the original third-party manager's account files, or Roblox's files. Its own older local vault can be imported through the first-run option. Master-password encryption protects the stored vault; malware on an unlocked PC can potentially read process memory. Do not put recovery codes or cookies in notes. Do not share your used Data folder.

Startup and periodic session checks contact Roblox's identity, moderation, and age-group APIs using saved cookies. Update checks contact GitHub at startup, on request, and every 30 minutes while automatic updates are enabled. Other requests happen when opening browsers, signing in, launching, or browsing servers. The embedded browser loads Roblox's normal resources and may make Microsoft runtime traffic. Explicit solver helper calls contact only `api.capsolver.com` or `api.solvex.run` with the supplied provider key and task data. No app telemetry is implemented.

## Updates

The app checks this repository's latest stable GitHub release at startup. **Automatic updates are off by default.** With the default setting, **Check for updates** retries manually and **View update** opens a read-only **What's new** window with the version change, download size, and a short release log. **Install update & restart** starts installation; Cancel closes the log without installing.

Open **Settings** and enable **Automatically install updates** to opt in. The manager then checks at startup and every 30 minutes, downloads verified releases, installs them, and restarts automatically. If a browser, sign-in queue, account operation, status check, or dialog is open, installation waits until that work finishes. Pending notes are saved before restarting. Disabling the toggle restores manual installation. An automatic installation failure pauses further automatic attempts; use **View update** to retry manually. The preference is saved in your portable vault; clean releases and layout imports default to off.

The updater verifies an ECDSA P-256 publisher signature using the public key embedded in the app, then checks the signed ZIP size, SHA-256, archive paths, and individual file checksums. It accepts only this project's release files and approved GitHub download hosts. An invalid signature, damaged download, or unexpected file stops installation. There are no GitHub login tokens or Roblox credentials in update requests.

The installer waits for the old process to exit and retries briefly if Windows retains an executable file lock. If the older v1.5.3 updater cannot replace its EXE, close the manager and manually copy the new ZIP's EXE, text files, and Docs into your used folder, keeping Data.

Only application files and Docs are replaced. Data is preserved, and interrupted installation attempts roll back replaced app files where possible. Recovery copies are kept under `.updates`; keep that folder if an update reports a recovery failure. Updating requires a writable ordinary application folder, without symbolic links or junctions. The app may briefly close during installation and restart on the same vault. Offline or rate-limited checks leave the app usable.

Versions before 1.4.0 need one manual download to get this updater. The app is unofficial and is not an independently audited security product.

## Launch arguments

To unlock an existing protected vault from CMD:

```cmd
RobloxAccountManager.exe "your master password"
```

You can also use `--password "your master password"`, and combine it with `--data-dir "D:\Manager\Data"`. Quote values containing spaces. `--help` lists the options. The password is the vault's master password, not a Roblox account password. A wrong password returns to the regular unlock screen; first-run setup and legacy conversion still require the setup screen. Command-line passwords may be visible in process listings and shell history. The app never logs argument values.

Updates started from v1.5.3 or newer automatically reopen the currently unlocked vault. They use a one-use token protected by Windows for the current user, bound to the vault and update path, expiring after five minutes. The token is consumed on restart. The master password is not written to disk or forwarded in the restart command. A later normal launch still asks for the master password. If the token cannot be used, the normal unlock screen appears. Versions before v1.5.3 need the usual unlock once after installing this feature.

## Build from source

Run **Build.cmd** with a .NET 10 SDK to create `dist/v1.10.0` and `releases/RobloxAccountManager-1.10.0-win-x64.zip`. The EXE bundles the app and .NET runtime and contains the original icon. WebView2 Runtime is installed separately. The SDK under `.tools/dotnet` is used if present; NuGet uses nuget.org and the dependency lockfile.

The extracted app contains only the EXE, `START-HERE.txt`, `SHA256SUMS.txt`, and `Docs` (this guide, licenses, and the browser-code example). Native runtime components use the standard per-user .NET temporary cache. Your account data stays in Data beside the EXE.

**The build never copies accounts.** It publishes into a fresh staging directory and archives only compiler output and named public files. Local Data, profiles, vaults, backups, tools, update staging, tests, and development notes are ignored by Git and excluded from release packaging. Share the generated ZIP, never a used app folder.

The optional `scripts/ReleaseSigner` tool signs official release manifests using a publisher private key stored locally under `.tools/signing/publisher.dpapi`, protected by the publishing Windows account. The private key is never included in source or releases. A checkout without that key builds an unsigned local ZIP; it cannot publish an update trusted by official clients. The app's public verification key is included in the source.

To upgrade a used portable folder manually, close the app and replace the EXE, text files, and Docs from the new ZIP, keeping your existing private Data folder. For an isolated preview, launch the EXE with `--data-dir` and a separate empty test directory.

Release checks exercise storage migration, warning acknowledgments, browser isolation, signature/hash validation, unsafe-archive rejection, and update rollback using synthetic data. Live Roblox login, group joining, game joining, and multi-instance behavior still require live account testing.
